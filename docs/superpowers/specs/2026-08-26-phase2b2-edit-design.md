# 薬局業務日誌 フェーズ2b-2：日誌編集 設計書

作成日: 2026-08-26

## 1. 背景と目的

フェーズ2b-1で、Firestoreに入っている日誌を月別一覧・1日分の詳細として**読み取り専用**で閲覧できるようになった。フェーズ2b-2では、既存日の詳細画面から**その場で修正・保存**できるようにする。

全体設計は [DB化・Web化 設計書](2026-08-25-pharmacy-log-db-migration-design.md) の 6.1「日誌詳細・編集」に基づく。フェーズ2bはさらに以下へ分割して進める。

- **フェーズ2b-1**: 日誌一覧・詳細(閲覧のみ) — 完了
- **フェーズ2b-2**: 日誌詳細の編集・保存(本設計書) — 次はここ
- **フェーズ2b-3以降**: 月報、マスタ設定 — 別途設計

### 非目的 (YAGNI)

- **新規日の作成。** 今回は既存日(Firestoreに既にドキュメントがある日)の修正のみを対象とする。自動取込が無い現状で新しい日のデータを追加する手段は、引き続き過去データ移行と同じ手動運用に頼る。新規作成の要件はフェーズ3(自動取込)の設計時にあらためて検討する
- **マスタ(医師名・予製品目・チェックリスト項目)の追加・編集。** マスタ設定は別フェーズ。本フェーズでは既存マスタに基づく行の数値・チェック状態のみ編集できる(詳細は4節)
- **フィールド単位のエラーハイライト。** バリデーションエラーは画面上部に一覧表示するのみとし、該当入力欄への赤枠等は付けない
- **同時編集の競合検出。** 本人のみが編集するため、楽観的ロックや競合検知は行わない(最後に保存した内容で上書きする)
- **一覧画面への「Web修正」バッジ表示。** `_meta.source` は保存するが、一覧画面(list.js)への表示は現時点では対象外とする。取込元が混在するようになった時点(フェーズ3以降)で検討する
- **`submissions`(提出資料)・`checklist`(チェックリスト実施記録)の編集。** いずれもデータモデル上は存在するが、現在の詳細画面(detail.js)に表示セクションが無く、過去データ移行でも値が入っていない([DB化・Web化 設計書](2026-08-25-pharmacy-log-db-migration-design.md) の4.1節で「新規」と明記されたフィールド。`masters.checklist` というマスタ側の項目定義とは別物)。Excelテンプレートが実装され実際に値が入るフェーズ3以降で、表示・編集の両方をまとめて追加する

## 2. アーキテクチャ

既存の `src/app/views/detail.js`(閲覧)と対になる `src/app/views/edit.js`(編集)を新設し、`main.js` が両者を切り替える。

```
main.js
  ├─ 一覧 (ListView, 既存)
  ├─ 詳細・閲覧 (DetailView, 既存)
  │     └─「編集」ボタン
  └─ 詳細・編集 (EditView, 新規)
        ├─「保存」ボタン → 検証 → Storage.saveLog → DetailView へ戻る
        └─「キャンセル」ボタン → 破棄 → DetailView へ戻る
```

- `src/app/views/edit.js`(新規、`window.EditView` として公開する IIFE): `EditView.render(container, log, onSave, onCancel)`。detail.js の各セクション関数(`rxSection` 等)に1:1対応する編集版のセクション関数を持ち、表示用の `<td>` テキストの代わりに `<input>`/`<select>` を生成する。行追加型セクション(5節参照)には「+ 行追加」「削除」ボタンを付ける
- `src/app/main.js`(変更): 詳細表示中の状態に「編集モード」フラグを持たせ、「編集」「保存」「キャンセル」のイベント処理と、保存時のフォーム収集→検証→保存の一連の流れを実装する
- `src/app/storage.js`(変更): `saveLog(date, data)` を追加。単一ドキュメントへの `setDoc` で、`_meta.source = "web"` / `_meta.webEditedAt = <ISO日時>` を付与する

## 3. データフロー

1. 一覧から日を選んで詳細を開く(既存、変更なし)
2. 詳細画面の「編集」ボタン → `EditView.render(container, log, onSave, onCancel)` で、同じ `log` を入力可能なフォームとして再描画する
3. 「保存」ボタン →
   1. フォームの値を1つのプレーンオブジェクトに集約する(edit.js内の関数)
   2. `DailyLog.normalize(data)` で正規化する
   3. `DailyLog.validate(normalized)` で検証する
      - **エラーあり**: 保存せず、画面上部にエラー一覧(`field` / `message`)を表示し、編集モードを継続する(入力内容は保持される)
      - **エラーなし**: `Storage.saveLog(date, normalized)` を呼ぶ
        - **保存成功**: `DetailView.render` に切り替え、保存した最新の内容を表示する
        - **保存失敗**(通信エラー等): エラーメッセージを表示し、編集モードを継続する。入力内容は保持される
4. 「キャンセル」ボタン → 入力内容を破棄し、編集を開始したときの `log`(メモリ上に保持済み)で `DetailView.render` に戻す。Firestoreへの再フェッチは行わない

## 4. 編集範囲の制約

detail.js にある全セクションを編集対象とするが、行の集合がマスタに紐づく2セクションは**既存行の値のみ編集可能**とし、行の追加・削除は不可とする(マスタ編集が別フェーズのため)。

| セクション | 編集内容 |
|---|---|
| 外来処方箋・外来注射箋・薬剤管理指導(`rxOpCnt`等) | 数値を自由編集 |
| 病棟注射箋(`winjData`) | 病棟ごとの枚数・件数を自由編集(病棟の追加・削除は不可、常に5病棟固定) |
| 病棟処方箋(`wardRx`) | 病棟×区分(定期/臨時/退院/持参薬/合計)ごとの**件数(`cnt`)のみ**を自由編集(病棟・区分は固定)。現在の詳細画面も`cnt`のみ表示しているため編集も揃える。`dose`(枚数)・`ippoka`(1包化、詳細画面では持参薬鑑別カードの算出元として使うのみで表として表示していない)は編集フォームに出さず、保存時は読み込んだ時点の値をそのまま保持する |
| 分包機メンテ(`packerData`) | 分包紙・インクの数値、清掃のチェックを自由編集(構造は固定) |
| **予製(`premixes`)** | **既存行の包数(`cnt`)のみ編集可。行の追加・削除は不可** |
| **処方変更・医師別(`doctorChanges`)** | **既存行の件数(`cnt`)のみ編集可。行の追加・削除は不可** |
| 疑義照会(`inquiries`) | 区分(`INQ_TYPES`からselect)・医師名・内容・処方変更有無を自由編集。行の追加・削除可 |
| MR訪問(`mrVisits`) | 会社名・内容を自由編集。行の追加・削除可 |
| 問い合わせ(`contacts`) | 区分(`CONTACT_FROM`からselect)・内容を自由編集。行の追加・削除可 |
| 薬品管理(`drugs`) | 区分(`DRUG_TYPES`からselect)・薬品名を自由編集。行の追加・削除可 |
| 欠品(`shortages`) | 薬品名・数量を自由編集。行の追加・削除可 |
| 会議(`meetings`) | 種別(`MEETING_TYPES`からselect)を自由編集。行の追加・削除可 |
| 研修会(`trainings`) | テーマ・担当者・参加人数を自由編集。行の追加・削除可 |
| 特記事項(`notes`) | 自由記述を自由編集 |

## 5. エラー処理

- **バリデーションエラー**: `DailyLog.validate()` が返す `{field, message}` の配列をそのまま画面上部に列挙する。`migrate.js` の取込失敗表示と同じパターンを踏襲する。フィールド単位のハイライトは行わない
- **Firestore書き込み失敗**: エラーメッセージを表示するのみ。入力内容は保持し、再度「保存」を押せば再試行できる

## 6. テスト方針

- `edit.js` / `main.js` の変更部分(DOM組み立て・フォーム値の収集)は、既存の `list.js` / `detail.js` と同様に自動テスト対象外とする。このプロジェクトは依存パッケージを持たない方針のため、jsdom等を使ったDOMテストは行わない。目視確認(実機・開発サーバ)で検証する
- `Storage.saveLog` は `listLogsByMonth` と同様、薄いFirestoreラッパーとして自動テストを持たない
- `DailyLog.validate` / `normalize` は既にテスト済みのものをそのまま呼び出すだけなので、新規のユニットテストは不要
